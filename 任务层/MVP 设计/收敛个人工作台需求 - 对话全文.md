## 1. Task 的持续执行与阶段性交付

一个 Task 在执行过程中，会不断产生：

- 对话记录。
- 动态认知摘录。
- 人类确认的 Master Prompt。
- 新获取的原始信息。

例如，Agent 生成了一份需求文档，但你认为内容还不成熟，那么：

- Task 继续保持执行状态。
- Agent 可以继续修改。
- 新版本继续留在执行区。
- 不成熟的版本不进入正式产物区。

直到人类认为阶段性成果已经成熟，才进行交付。

## 2. 产物区：有点像 Git 的概念

我认为你这个类比很有价值。

产物区不是一个简单的文件存储目录，而是项目的正式成果空间。

它有几个特点：

**第一，正式版本。**

只有经过人类认可的成果，才进入产物区。

**第二，版本演进。**

同一份产物可以不断更新，但产物区始终呈现当前最新的正式版本。

**第三，保留历史。**

更新最新版本不应该意味着覆盖并丢失旧版本。应该能够追溯历史版本，以及每次更新的来源。

**第四，驱动后续工作。**

正式产物可以成为下一个 Task 的输入和依据。

### 三、Master Prompt 和 Milestone 的确认机制

我建议：

- **Master Prompt**：经过人类确认、可以被后续 Agent 直接采用的工作共识或指令。
- **Milestone**：某个阶段已经达成的成果或设计共识，代表一次进展确认。

它们可以引用同一段讨论，但不应该被当作同一种对象。

### 四、上下文输出机制需要定义

- 输出是完整记录，还是经过整理的精简上下文？
- 新 Agent 如何知道哪些内容是已确认共识，哪些只是讨论中的假设？
- 如果原来的共识后来发生变化，如何避免新 Agent 继续使用过期结论？

**ChatGPT**

我赞同。MVP 不应该为了体现设计能力而创造一套复杂的状态机。

建议先采用最常见的五种 Task 状态：

| 状态 | 含义 |
|---|---|
| Todo | 待开始 |
| In Progress | 执行中 |
| Blocked | 阻塞中，需要解决问题才能继续 |
| Done | 已完成并通过交付确认 |
| Cancelled | 已取消，不再继续 |

这里有两个约束：

1. Agent 可以推动任务状态变化，但涉及正式交付的 Done，必须经过人类确认。
2. 任务产生中间文件不意味着 Done，只有满足交付目标才算完成。

另外，**白板状态与 Task 状态分开管理**。例如 Task 仍在 In Progress，但某个白板已经讨论完成。

先用这五种状态，后续遇到真实业务场景再扩展。

这可以作为 Milestone 006：采用标准化、最小化的 Task 状态机。
