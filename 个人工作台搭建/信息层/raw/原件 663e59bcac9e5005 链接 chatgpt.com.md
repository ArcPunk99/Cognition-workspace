# Personal Workspace — Handoff 文档

**主题：Project 探索机制、Trigger 卡片与 MVP 技术验证**

**日期：** 2026-11-25  
**阶段：** 产品设计收敛 → 技术验证准备  
**状态：** 部分设计已确认，部分技术方案待实验验证

---

## 一、文档目的

本文档用于向后续 AI Agent、开发人员或新的讨论会话交接当前 Personal Workspace 的设计进展。

本轮讨论主要解决三个问题：

1. Project 级探索与 Task 级执行如何分工。
2. 如何通过自然对话识别 Trigger，并逐渐形成 Task 或 Milestone。
3. Trigger 卡片应采用什么样的 MVP 数据结构。

**核心原则：保留已经确认的产品共识，不把尚未验证的技术假设写成确定结论。**

---

## 二、系统整体定位

Personal Workspace 是一个由人和 AI 共同推动认知生长、同时完成实际任务的工作空间。

系统围绕 Project 组织信息、认知和行动。

### 2.1 Project 级探索

主对话 Agent 的核心职责是探索整个 Project 的认知空间，而不是直接承担所有任务执行。

它需要能够访问：

- Project 的已有信息和原始资料。
- 已确认的认知 Milestone。
- 当前 Task 及其执行结果。
- 尚未解决的问题和认知缺口。
- 模型自身的知识与推理能力。

主 Agent 与人持续讨论：

- 当前已经知道什么？
- 哪些判断尚未确认？
- 哪些问题值得继续探索？
- 是否出现了需要执行的行动？

### 2.2 Task 级执行

Task 承接相对明确的行动目标。

Task 执行过程中仍可能发生局部探索，并产生子 Task。

执行过程中获得的新资料、判断和成果，需要回流到 Project Library。

### 2.3 认知反馈循环

整体逻辑为：

**Project 探索 → 识别 Trigger → 人工判断 → Task 执行 → 产生资料与认知 → Milestone 确认 → Library 更新 → Project 继续探索。**

需要注意：

- 不是每次探索都产生 Task。
- 不是每个 Task 都产生 Milestone。
- 普通问答允许自然结束。
- AI 的总结不能自动等同于人类已经形成的认知。

## 三、主对话交互机制

### 3.1 单一自然语言入口

已确认：

**主对话是统一的自然语言交互入口。**

用户可以通过文字或语音进行探索、提出行动意图、回答澄清问题以及确认判断。

右侧区域负责同步展示结构化结果。

不为每张 Trigger 卡片单独创建对话入口。

### 3.2 Agent 的职责

主 Agent 负责：

1. 理解当前对话。
2. 识别潜在 Trigger。
3. 结合 Project 上下文判断信息是否充分。
4. 在必要时通过主对话追问。
5. 更新已有 Trigger。
6. 提出 Task 或 Milestone 候选建议。

Agent 不应该为了填满字段而反复追问，也不应该因为识别到问题就强制创建任务。

### 3.3 Trigger 的两种形成方式

**显式 Trigger**

用户明确表达行动意图，例如：

“我现在需要研究一下 DSH。”

系统可以立即生成候选 Trigger。

如果用户直接明确要求创建任务，则可以直接创建正式 Task，不必重复确认同一指令。

**渐进式 Trigger**

用户在多轮讨论中逐渐明确一个问题、目标或判断。

Agent 根据对话逐步形成和完善候选 Trigger。

当信息不足时，Agent 可以在主对话中进行针对性追问。

### 3.4 人工判断权

Agent 负责识别和建议，人负责决定是否将候选意图转化为正式对象。

可能的结果包括：

- 创建 Task。
- 确认 Milestone。
- 继续探索。
- 忽略候选 Trigger。
- 问题解决后自然结束，不产生任何对象。

---

## 四、Trigger 的产品定义

**Trigger 是对话中潜在行动或认知意图的临时结构化表达。**

Trigger 不是 Task，也不是 Milestone。

它用于连接自然语言探索与正式业务对象。

Trigger 的生命周期包括：

**识别 → 澄清 → 人工处置 → 转化或关闭。**

右侧 Trigger 卡片承担可视化和操作入口职责，不承担完整任务管理职责。

## 五、Trigger MVP 数据结构

### 5.1 字段定义

| 字段 | 类型 | 含义 |
|---|---|---|
| `id` | string | Trigger 唯一标识 |
| `title` | string | 简短标题 |
| `type` | enum | 意图类型 |
| `intent` | string | 当前理解的意图 |
| `context` | string / null | 产生意图的背景 |
| `status` | enum | Trigger 当前状态 |
| `source` | object | 原始对话引用 |
| `target` | object / null | 转化后的正式对象引用 |

MVP 暂定以上八个字段。

### 5.2 类型枚举

`type` 允许三个值：

- `action`：行动意图，可能转化为 Task。
- `knowledge`：认知成果候选，可能转化为 Milestone。
- `undecided`：尚未明确分类。

类型可以随着对话推进而更新。

### 5.3 状态枚举

`status` 允许四个值：

- `candidate`：已识别的候选 Trigger。
- `clarifying`：正在澄清。
- `accepted`：用户已确认处置。
- `dismissed`：用户已忽略或关闭。

正式 Task 的执行状态不放在 Trigger 中。

### 5.4 JSON 示例

```json
{
  "id": "trg_001",
  "title": "研究 DSH 的适用性",
  "type": "action",
  "intent": "研究 DSH 是否适合当前项目",
  "context": "需要验证 Personal Workspace 的技术方案",
  "status": "clarifying",
  "source": {
    "conversation_id": "conv_001",
    "message_ids": [
      "msg_12",
      "msg_15"
    ]
  },
  "target": null
}
```

该结构是 MVP 候选设计，并非已经完成技术验证的最终 Schema。

### 5.5 数据约束

**约束一：区分推断与确认**

Agent 可以根据上下文推断用户意图，但不能把推断直接视为用户已确认的判断。

当前八字段结构尚未完整解决字段级确认和来源标记问题，需要在验证时特别关注。

**约束二：同一意图持续更新**

同一 Trigger 应尽量更新原有卡片，而不是每轮对话创建重复卡片。

**约束三：保留来源引用**

Trigger 需要能够追溯到原始对话。

不要求在 Trigger 内复制完整对话。

**约束四：转化后建立关联**

Trigger 转化为 Task 或 Milestone 后，通过 `target` 保存正式对象引用。

**约束五：保持临时性**

Trigger 不承担长期知识管理职责。

转化或关闭后可以归档。具体保留期限尚未确定。

## 六、右侧卡片交互

右侧卡片只展示用户需要理解和操作的信息。

示例：

**研究 DSH 的适用性**

类型：行动意图  
状态：澄清中

**当前理解**

研究 DSH 是否适合 Personal Workspace。

**待澄清问题**

研究目的是验证底层架构的适用性，还是寻找能够直接复用的实现？

**可用操作**

继续讨论 / 创建任务 / 忽略

所有自然语言澄清均发生在主对话中。

右侧卡片随对话更新。

多个 Trigger 可以同时存在，但 Agent 应优先围绕当前讨论主题进行澄清，避免主动切换话题。

## 七、Milestone 与 Library 的关系

已确认的原则：

**Library 保存完整信息，Milestone 承载经过人确认、具有持续价值的关键认知。**

原始资料、AI 摘要和人类认知判断需要保持区分。

AI 可以压缩资料、提炼阅读导航，但不能以摘要代替人类阅读和理解。

Task 执行获得的资料应当能够回流 Library。

有价值的认知成果可以经过人工确认后形成 Milestone。

### 尚未确定：索引策略

讨论中提出过以 Milestone 为主要认知索引的方案。

其潜在优势是避免对整个 Library 进行高成本语义索引。

但用户明确表示：

**目前无法确定该方案是否正确，需要通过实际执行和实验判断。**

因此：

- 不将 Milestone 索引确认为唯一技术路线。
- 不预先排除全局上下文方案。
- 暂不深入讨论非文本资料的上下文处理。
- 不在当前阶段设计复杂索引架构。

## 八、MVP 技术验证方向

### 8.1 候选技术组合

当前拟采用：

- **DeepSeek**：承担主对话、语义理解与 Trigger 识别。
- **DSH**：候选 Agent 运行框架，具体能力和适配性待验证。

该组合是实验起点，不代表最终技术选型。

### 8.2 第一轮验证目标

**优先验证：单一对话 Agent 能否在真实连续对话中稳定识别、维护和更新结构化 Trigger。**

不以完整 Personal Workspace 的开发作为第一轮目标。

### 8.3 验证场景

使用本轮真实对话作为测试输入。

重点覆盖：

1. 用户提出模糊想法。
2. Agent 识别候选 Trigger。
3. Agent 判断信息缺口并追问。
4. 用户逐步明确意图。
5. Agent 更新原有 Trigger。
6. 用户提出明确行动指令。
7. 用户修改或撤回此前判断。
8. 普通问答结束，不产生新对象。
9. 用户确认创建 Task 或 Milestone。
10. 多个 Trigger 在连续对话中保持独立状态。

### 8.4 验证指标

重点观察：

- Trigger 识别准确性。
- 普通问答误触发情况。
- 应识别 Trigger 的遗漏情况。
- 重复卡片产生情况。
- 多轮状态一致性。
- 对用户修正意见的响应能力。
- 人工确认边界是否可靠。

当前不预设具体通过率阈值。

### 8.5 暂不实施

第一轮不必实现：

- 复杂多 Agent 编排。
- 全库语义索引。
- 多模态资料统一处理。
- 完整任务管理系统。
- 自动化 Milestone 知识图谱。
- 复杂的任务调度与资源协调。

这些能力不等于被否定，只是不属于当前最小实验的验证重点。

## 十、下一阶段建议

下一阶段不继续扩大产品架构讨论，而是将现有设计转化为可测试的行为规范。

建议优先完成三个产物：

**产物 A：Trigger Schema**

把当前八字段模型整理成可验证的数据契约，定义字段类型、枚举、空值和引用规则。

**产物 B：Trigger Agent 行为规范**

明确什么时候创建、更新、澄清、忽略 Trigger，以及如何避免重复识别和错误确认。

**产物 C：真实对话测试集**

从本轮讨论中提取典型场景，为每段对话标注预期行为，再使用 DeepSeek 进行实验。

第一轮实验完成后，根据实际问题决定是否需要增加 Workflow、辅助 Agent 或其他状态管理能力。

## 十一、后续 Agent 交接指令

接手本项目的 Agent 应遵循以下原则：

1. 不要重新推翻已经确认的产品设计，除非用户明确提出修改。
2. 不要把技术建议直接升级为产品共识。
3. 明确区分用户确认、Agent 推断和待验证假设。
4. 优先采用最小可行方案，避免无必要的架构复杂化。
5. 不要将普通探索性对话强制转化为 Task 或 Milestone。
6. 对尚未明确的技术问题，优先提出实验方法，而不是过早确定架构。
7. 保持原始资料、AI 加工结果和人类确认认知之间的边界。
8. 后续设计应继续围绕 Project 探索、Task 执行、认知生长的闭环展开。

### 最终交接结论

**Personal Workspace 的核心不是任务管理，也不是单纯的 AI 聊天，而是通过自然语言探索和目标执行，使 Project 的认知空间持续生长。**

当前最值得优先验证的能力是：

**一个对话式 Agent 能否将自然对话中的行动意图和认知成果，可靠地转化为可视化、可追溯、由人最终处置的结构化 Trigger。**

这是下一轮技术实验的主要起点。
