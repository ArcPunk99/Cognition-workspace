# MVP 定义 — 前端路线（草稿）

> 状态：草稿，留在任务层。经扭老板确认后进 `产物层/工作台设计/`。
> 依据：[[收敛个人工作台需求 - 对话全文]] 第 57–66 轮。命名沿用对话中的「信息区 / 执行区 / 产物区」，与现行目录的「信息层 / 任务层 / 产物层」指同一件事，落地时需统一。

## 0. 这一版改了什么

第 65 轮定的是「Obsidian 好用就一直用，不再单独开发前端」。第 66 轮建立在此之上，定义了五种状态。

2026-11-23 提出的问题是：**没有前端，就很难产生明确的状态机、管理任务进度、产生 trigger，也就很难和 AI 能力交互。**

这句话指向的不是「界面好不好看」，而是三件前端才有的事：

| 能力 | 纯 Obsidian | 结论 |
|---|---|---|
| 状态定义与合法迁移 | 属性写在哪就在哪，没人拦 | 需要承载 |
| 迁移拦截（禁止非法状态存在） | 只能事后查 | 需要承载 |
| 事件触发（状态变了 → 自动做事） | 无事件层 | **必须跳出** |
| 主动找人（阻塞超时、待确认队列） | 无后台常驻 | **必须跳出** |

所以本版把路线调整为：**Markdown 文件为唯一真相，另加一层前端负责状态闸门与触发。** 第 65 轮里可保留的部分是「数据不被锁死」——文件仍是可读、可迁移、可被任意 Agent 直接操作的。

**这是一次路线级变更，尚未记入项目页。** 若确认，按 [[Schema#目标或策略变更追加在项目页]] 的格式追加一条变更记录。

## 2. 状态机

五种状态：`Todo` / `In Progress` / `Blocked` / `Done` / `Cancelled`。

### 2.1 迁移表

| 从 | 到 | 谁提 | 硬条件 | 必须留下 |
|---|---|---|---|---|
| — | Todo | 人（创建弹窗） | 有目的与目标 | 任务页、目的、目标 |
| Todo | In Progress | AI | 无 | 开工时间 |
| In Progress | Blocked | AI | 写清缺什么 | 阻塞原因 + 所需输入 |
| Blocked | In Progress | 人 | 阻塞项已满足 | 解除依据 |
| In Progress | Done | AI 提议，人确认 | 产物层有本任务的已确认版本 | 确认人、时间、产物链接 |
| Todo / In Progress / Blocked | Cancelled | 人 | 明确放弃 | 取消理由 |
| Done | In Progress | 人 | 需返工 | 重开理由；旧产物保留 |

### 2.2 三道闸门

这三条是把「状态机」和「一个下拉框」区分开的地方。任何一条不满足，写入 `Done` 即视为非法，前端拒绝，脚本事后也能查出来。

1. **AI 不能单方面置 Done。** 没有确认人与确认时间，Done 不成立。
2. **中间文件不等于交付。** 产物层没有该任务的已确认版本时，Done 不成立。
3. **白板状态与 Task 状态解耦。** Task 在 In Progress，某个白板可以已讨论完成；反之亦然。

## 3. 触发规则

每条都是「事件 → 条件 → 动作」，标明要不要人点头。这张表就是前端需要的全部 trigger，不多不少。

| 事件 | 条件 | AI 动作 | 人确认 |
|---|---|---|---|
| 新建任务 | 弹窗提交 | 生成任务页骨架：目的、目标、下一步 | 否 |
| 对话里出现「这条留下」 | — | 生成 Milestone 候选页，附来源片段 | **是** |
| 对话里出现信息缺口 | 缺的是可检索资料 | 调取资料进信息区，登记来源、获取时间、所属问题 | 否（入库≠确认） |
| 白板标「讨论完成」 | — | 生成该话题的上下文包，供下一话题引用 | 否 |
| 任务 In Progress 连续 N 天无变更 | N 待定，建议 5 | 生成「卡住了」提醒 | 是（人决定怎么处理） |
| 新产物与已确认 Milestone 冲突 | — | 列出冲突项与两侧依据 | **是** |
| 人确认交付 | 产物层已有版本 | 状态置 Done，产物标为正式版 | 已确认 |

## 4. AI 介入边界

| 可自动做 | 必须人确认 |
|---|---|
| 读全库、调资料、写草稿、白板追加、生成上下文包 | Milestone 成立 |
| 提议状态迁移、标 Blocked | 产物入库、任务置 Done |
| 整理、归档、建立链接 | 目标或策略变更 |
| 提示冲突、列出依据 | Raw 的审阅状态（读了哪部分只有人知道） |

一条底线沿用 MS-001：AI 的建议不得自动升级为已确认判断。

## 5. 数据层

文件仍是唯一真相，前端是它上面的一层。

- 每条记录 = 一个 Markdown 文件 + frontmatter。状态、所属、依据都写在属性里。
- 状态变更写回 frontmatter，同时追加一行到该任务的 `日志.md`（时间、从、到、谁、为什么）。Git 本身也是第二份证据。
- 前端不拥有数据。删掉前端，库里的一切仍然可读、可被任意 Agent 接手。
- 选型未定，见第 7 节。

## 6. 验收：用一个真实任务跑通

不造模拟数据。就用本项目下一个真实任务，跑一遍：建任务 → 对话 → 标一条 Milestone → 标 Blocked → 解除 → 交付确认 → Done。跑通才算 MVP，跑不通说明上面某张表写错了。

## 7. 待你定的三件

1. **路线变更是否入库。** 65 轮的「不开发前端」要正式改成「文件为真相 + 前端承载状态与触发」吗？确认了我就按 Schema 追加到项目页。
2. **前端形态。** 三选一：Obsidian 插件（就地长在库里，最省，但受插件生态约束）／ 独立本地应用（读同一目录，最自由，要自己维护）／ 手机优先轻应用（能主动推给你，但库在电脑上）。
3. **第一刀切哪。** 我的判断是先做骨架不做界面：把状态机、闸门、触发规则做成一个能跑的后端 + 命令行，用真实任务验证一遍，界面后置。理由是界面可以返工，状态机错了会把整个库的数据写脏。
