本次讨论围绕 AI Agent 系统的核心架构设计展开，三位参与者从 Utopia 开源项目的调研出发，深入探讨了意图层、认知层、行动层的三层框架模型，并延伸至 Case Knowledge 可视化方案、本体论（Ontology）建设路径、任务状态机管理以及前端交互设计等议题。讨论还涉及个人工作台的实践验证方法、创业方向选择（CEO 人选、投资人视角与创业者视角的碰撞）以及 Skill 与本体在 Agent 体系中的分工定位，最终确认了核心骨架已经收敛清晰，下一步重点在于各模块功能的具象化定义。

## Utopia 开源项目调研

**项目概况与功能定位**

Utopia 是一个基于本体论的 Agent 协作项目，功能涵盖知识图谱与向量存储，支持知识随数据到达而演进、冲突检测、推理决策，且能够离线部署。

项目当前版本为 V0.1（或 V0.0.1），但已有 1000 多次 commit，GitHub Star 数达到 8.7k。

项目由一个团队组织维护，非单一开发者。

**二次开发可行性**

柳翔 认为可以直接在其基础上做二次开发。

## Agent 框架三层架构设计

**架构总述**

将所有事情拆解为意图层、认知层、行动层三层，所有循环建立在这三层之上，三者形成动态关联。最终加工出的阶段性产物（如研发报告、关系图谱）都是动态的，按需从框架中获取。

**意图层**

包含人的目的（AI 永远不可能产生的）、人的直觉判断（跳出规则的"玄学研判"），以及机器可读的 Ontology（本体），本体用于约束规则内的决策判断。

意图层承载两部分：宏观目的和目标。一个 case 中可能同时存在多个目的（如"找出犯罪嫌疑人""证明作案动机""将其诉讼"），这些不一定都会走到。

意图本身没有可可视化内容，只能作为 task 的上下文文本存在。

**认知层**

认知层承载原始信息（结构化与非结构化数据），信息到达后由意图层介入判断，产生行动。

信息有边界，不会无限扩展。

**行动层**

目标催生任务，任务是一个完整单元，包含意图、认知、具体方向、skill 和 worker，并带有状态机来管理执行进展。

任务不是固定 workflow 的一步一步执行，AI native 的方式应支持长任务的 loop 循环，任务本身具有一定的自由度（可能一步就结束，也可能需要继续深入）。

## 认知里程碑与任务执行机制

**里程碑的产生与记录**

在执行任务过程中，当发现对目标有重要推进的认知节点时，产生一个"认知里程碑"，需要被标记记录（相当于"插小旗子"）。

里程碑可以是人机共识，也可以是多人讨论后确认的判断，背后对应一个完整片段。

一个任务可能产生 10 个、20 个甚至几十个认知里程碑，不影响任务本身的大小。

**里程碑的传递与上下文**

任务内部包含完成该任务所需的上下文（意图 + 认知），里程碑在任务内部产生。

里程碑产生后推动整个认知向前进。

**任务产物的可审计性**

核心目标是产生所有可审计的轨迹链条，报告本身反而是可有可无的副产品。

报告可以在任何时间点按需生成，不必绑定在任务结束节点。

所有判断都可以被回溯，因为里程碑和资料都能与原始任务关联。

## 本体论（Ontology）的作用与建设路径

**本体的核心功能**

本体解决的是"不同数据背后的真实世界规则是什么"——A 与 B 之间的关系、约束条件等，让机器能够判断是否该产生某个决策、任务是否该继续推进。

Agent 执行任务时需要去本体过一圈，由本体来判断信息之间的关系。

**本体与 Skill 的关系**

Skill 是通用性工具（如查询平台），本体是约束层。不能把约束放进 Skill（"把菜刀定义为只能切鱼片"不合理），约束应放在本体。

本体决定了同一个 Skill 在不同场景下的不同走向。

**本体建设路径**

本体可以很轻，第一阶段可用自有的知识去投喂，通过专家经验先拖一个最基本的，再慢慢演化。本体本来就是演化式的，不是一次性建好的。

当前约束靠提示词实现，最终不能依赖提示词，必须建本体。

进入不同行业需要建对应行业的本体，但各行各业有相通的通用本体。

**本体缺失的后果**

如果没有本体来协调，整个系统会"乱哄哄的"。

## 多 Case 与多意图场景处理

**多意图并存**

一个 case 中可能出现多重意图（如刑侦、治安、政工对同一嫌疑人有不同关注点），意图层通过更新目的来容纳新的意图。

**分支拆分方案**

当发现某个方向完全脱离当前主线时，可以从现有 case 中将有用的信息复制出来，新建一个独立 case。类似于 git 分支思想。

但存在原始分支与新分支同时迭代的问题，此时回到责任定义——如果责任主体是一个人，不存在分支冲突；如果是组织，则需要处理。

**多任务并发冲突**

多个 case 或同一 case 拆出的多个任务可能对同一个人执行相同操作（如多个部门反复给被害人打电话问同一个问题），这是现实业务中已发生的问题。

解决方案：通过 Task 状态机管理，将正在执行中的任务聚合，阶段性完成并释放，打包后交付。

## Case Knowledge 可视化设计

**核心要素抽象**

Case Knowledge 围绕人、事、地、物四个核心元素展开。

初期场景（刑侦）以人为中心展开，地可能挂靠在人或事件上，不一定单独成维度。

不同领域可能核心要素不同，但当前以刑侦为首要场景。

**视图与画布**

认知画布和要素画布本质是同一个东西，只是不同视图。从人出发拓扑关系、从时间轴出发梳理事实、从物与物关联展示图谱。

可视化层最终分离为两个模块：一个是 Case Knowledge（包含里程碑等所有重要判断，原始资料可一键查看），一个是 Task 看板（展示任务状态和认知里程碑）。

**UI 风格讨论**

图谱连线如果线太多反而"跟没线没区别"，需要限制在 3D 空间或用高亮/半透明过滤。

考虑伪 3D 效果（卡片铺在 2D 面上，视图斜 45 度）+ 滚轮滚动，类似地图交互。

点击某节点时高亮关联线、其余节点变半透明，聚焦注意力。

展示版（给领导看）用大屏关系图谱，用户实际使用聚焦卡片和文档。

连线可以是动态的，基于时间轴让图谱"慢慢长出来"。

UI 做起来"确实要有点水平的"，一句话 prompt 做不了。

需要时间戳，每个判断有产生依据。

## 前端交互与个人工作台实践

**工作台验证方法**

发言人 1 正在搭建一个"个人工作台"来验证整套框架，相当于自己的 FDE（Forward Deployed Engineer），边做边沉淀边完善。

仓库结构：Schema（本体规则）+ README（意图层/整个背景目标）+ Project（相当于一个 case）。

每个 Project 内：信息层（原始信息 + 查到的外部资料）→ 人与 AI 共同判断有价值的点 → 标记认知里程碑 → 积累梳理 → 人决定是否推进。

Obsidian 作为本地文档存储空间，上面套插件驱动 Agent 能力。

**交互模式**

讨论模式（聊天式）中，判断某个点有价值时直接让 AI 记录，后续 Agent 基于上下文精准读取。

执行任务时：左侧任务卡片栏 + 右侧原始资料/文档 + 下方 AI 对话框，类似当前 AI 工具的布局。

支持多开，同时查看多个不同来源的信息做比对。

**技术工具选择**

正在磨合 Codex 的使用，Codex 会推荐下一步操作。

对于非专业用户（如美术/UI），模型能力差异不大，关键是能否约束 AI 做出想象的东西。

建议找专业人做 UI，自己只能定功能点和方向。

## 创业方向与团队讨论

**CEO/合伙人问题**

大学同学建议找 CEO 或合伙人的问题：同学愿意当投资人，但推荐的人选（百度背景、有 FDE 团队、接政府项目）因家庭原因（儿子自闭症，60 岁前需为儿子存够钱）不愿承担创业风险。

**两种视角的碰撞**

大学同学是投资人视角：要求确定性，没确定的东西不投。

王鹏是创业者视角：担心等打磨完市场没了、入场券没了。

发言人 1 认为两者都有道理，结论是并行推进——美克生先打品牌进军 FDE 领域，与公安合作落地。

**核心竞争力定位**

开源产品本身不是竞争力，如何把开源东西改造落地才是核心竞争力。

这套方法论和 UI 甚至可以开源，反而能成为门槛。

核心优势在于把产品做好让人愿意用，技术层没有壁垒。

## 整体判断与下一步方向

**架构收敛状态**

核心骨架已经收敛清晰，"已经是有雏形的"，用个人工作台验证了思路能跑通。

下面几层（框架、关系）已明确，上面 UI 层正在具象化。

**下一步重点**

定功能：每个模块长什么样子都要敲出来。

建本体：把提示词约束升级为协议约束。

搭 MVP：个人工作台跑通后形成 MVP，在内部业务中并行推进。

从不同行业吸收东西完善 baseline，再推向各行业。

**人机分工原则**

最不能被取代的是人做判断题（决策、直觉、灵感），人负责输入和授权（"我同意，他在动"），其余都可被 AI 取代。

人的直觉和决策判断"10 年都取代不了"，谁来负责任的问题是根本约束。

## AI 洞察（整理者所加，非与会者原话）

本次讨论实质上完成了一个 Agent 框架从抽象理念到落地路径的全链路梳理，核心突破在于将"认知里程碑"作为连接任务执行与知识积累的桥梁，使长任务不再是线性 workflow 而是可回溯、可审计、可分叉的有机过程。

"本体是约束层、Skill 是工具层"这一区分（菜刀比喻）可能是该框架与当前主流 Agent 设计（侧重 Skill 编排）的关键差异化所在，值得在后续技术方案中重点验证。

团队在"先做确定性产品"与"先搭通用框架"之间存在张力，当前结论（并行推进 + 个人工作台验证）是一种务实折中，但需注意避免陷入"框架完美主义"而延误产品化窗口。
