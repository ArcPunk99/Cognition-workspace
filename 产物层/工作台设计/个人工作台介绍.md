# 个人工作台 · 项目介绍

整理日期：2026-11-23。内容取自本库现行文档、V0.4 交接、《构建个人工作台框架》158 轮与《收敛个人工作台需求》66 轮两场对话。

---

## 一、这是什么

一套给自己用的个人工作台：把 Obsidian 里的一个目录，变成能持续推进项目的工作空间。

打开一个项目，能看见想做成什么、哪件事正在推进；隔一段时间回来，能接着上次的判断往下走，而不是从头再讲一遍背景。

它要解决的不是"记笔记"，是**判断的流失**。

---

## 二、背景

### 2.1 三个反复出现的具体麻烦

1. **长对话里，判断会沉底。** 几十轮讨论出来的一句话结论，三天后翻不回去，只能重讲。
2. **换一个 Agent，接不上手。** 每个 AI 都得从头交代"我们之前定了什么"，而它读不到那部分。
3. **过程和成果混在一起。** 中间稿、定稿、旧版本堆在一处，分不清哪个能当依据用。

三条指向同一个缺口：**缺一套能把"为什么这么定"留下来的记录结构**，而不只是保存最终结果。

### 2.2 定位上走过一次偏

最初的设计基线（V0.1）以「认知图谱」为核心，把 Obsidian 当唯一事实来源，定义了 Input / Cognition / Judgment / Goal / Task / Outcome 六类对象。

这份基线被推翻，理由很具体：它会优先做出一套复杂的认知节点和图谱，而不是先解决最痛的那个问题——**在长对话里低成本地保住判断，并让它推动任务**。

重构后的定位：

> **以项目和任务推进为核心、以人的判断为依据、由 Agent 辅助管理工作过程的个人工作台。认知沉淀是工作推进的成果，不是需要独立经营的目标。**

这次转向确立了后来全部设计的排序：先任务，后认知；认知跟着任务走，不另开一条线。

### 2.3 「系统底座是谁」改过两次

| 阶段 | 主张 | 结果 |
|---|---|---|
| V0.1 | Obsidian Vault 是唯一事实来源 | 否。会把状态、流程全塞进 Markdown 和 YAML，复杂且易不一致 |
| 框架设计第 106 轮 | 本地项目目录为底座，SQLite 管结构化状态，Obsidian 只管文档交互，工作台管项目与进度 | 设计上采纳 |
| 本地实做（2026-11-22） | 只有 Markdown 属性 + Bases，没有 SQLite | 跑通了，但省掉了状态层 |
| 2026-11-23 | 提出：没有前端就难以产生明确状态机、管理进度、产生 trigger | 待定，见第五节 |

这不是反复无常，是同一个问题被问了三次：**状态到底由谁保证。** 每次答案不同，因为每次对"保证到什么程度"的要求不同。

### 2.4 一次顺带的发现

讨论到一半，扭老板问：自己会不会在重复发明已有理论或工具已经解决的东西。

这一问把工作从"继续定目录、写字段"改成"先查资料再定"。查的过程又反过来给出了一个要求：资料到手、成果做出、判断成立，是三种不同性质的记录，必须分得开。这条要求就是后来的 MS-001。

## 三、框架

### 3.1 三层职责

| 层 | 管什么 | 本库落点 |
|---|---|---|
| **意图层** Intent | 目的、目标、目标调整、战略方向 | 项目入口页正文 |
| **认知层** Cognitive | 原始资料、已确认判断、依据、认知演进 | `信息层/raw/`、`信息层/认知里程碑/` |
| **行动层** Action | 任务、执行过程、成果、历史版本 | `任务层/`、`产物层/` |

三层是职责划分，不要求目录一一对应。借鉴 OGSM，但不把 Objective / Goal / Strategy / Measure 机械拆成四个目录——Strategy 不等于 Task，这层区分留在文字里，不变成字段。

### 3.2 基本循环

```text
意图 → 策略 → 行动 → 结果反馈 → 认知更新 → 意图修正 → 策略调整
```

认知变化可以触发目标调整，但**不得未经授权自行修改已确认的目标**。要改，在项目页追加一条变更记录：原表述、新表述、触发它的判断、理由、确认人与时间。

### 3.3 三类记录与一道闸门

| 记录 | 是什么 | 关键约束 |
|---|---|---|
| **Raw** 原始资料 | 收到的材料、链接、原件、对话交接 | 默认不是事实，也不是已确认判断 |
| **Milestone** 认知里程碑 | 一句已确认的判断，原子化、可引用 | **必须经人确认**，AI 的建议不得自动升级 |
| **Artifact** 成果版本 | 经人确认的阶段性交付 | 最新产物不因新而自动获得更高认知权威 |

三者的关系不能只记"有链接"，还要能说出性质：supports / contradicts / derived_from / supersedes / triggered_by。本库目前只做到了 supports 与"确认出处"，其余仍是提案。

**这道闸门是整个系统的核心**：收集资料、审阅资料、确认判断，三件事分开。资料可以 AI 去调，判断只能人点头。没有这道闸门，"人机共同维护认知空间"会退化成又一套要人工整理的知识库。

### 3.4 上下文收敛

任务内允许发散，任务结束时靠 Artifact 收敛。

正式 Artifact 成为下一项任务的输入；旧任务的 Milestone 退出默认活跃上下文，Raw 留着备查。这是避免上下文膨胀和旧判断干扰新判断的机制——**不收敛，工作台会越用越慢**。

### 3.5 人机分工

| AI 可自动 | 必须人确认 |
|---|---|
| 读全库、调资料、写草稿、整理归档、建链接、提示冲突 | Milestone 成立、产物入库、任务置 Done、目标变更、Raw 的审阅状态 |

## 四、具体形态

### 4.1 现在库长什么样

```text
Project/                       ← Obsidian vault
├── 欢迎.md
├── README.md                  ← 工作台怎么用
├── Schema.md                  ← 项目/任务/Raw/Milestone 的记录规范
└── 个人工作台搭建/             ← 一个项目
    ├── 个人工作台搭建.md        ← 项目入口页，嵌入进度表
    ├── 个人工作台搭建进度.base   ← Bases 视图：按项目筛选任务/资料/里程碑
    ├── 信息层/
    │   ├── raw/               ← 4 份：V0.4 交接、BDI 论文+译稿、W3C PROV
    │   └── 认知里程碑/         ← MS-001
    ├── 任务层/<任务名>/        ← 任务页 + 对话全文 + 草稿
    └── 产物层/工作台设计/      ← 经确认的设计文档
```

**跑通的部分**：项目页嵌一张表 → 点任务名进任务页 → 状态与笔记属性一致 → 从 Milestone 点回交接原文的确认句，落点高亮。用的是 Markdown、附件和一个 `.base` 文件，没有数据库、没有插件依赖。

**看得见的短板**：一个真实任务已经跑过（"验证能否按项目查看任务"），但它验证的是"能不能看到"，不是"状态对不对、该不该迁移"。

### 4.2 MVP 想长成什么样

来源是 66 轮对话收敛出的六条产品决策：

1. 欢迎页 = 项目卡片入口；创建统一从弹窗发起，不跳页
2. AI 原生：自然语言驱动，Bot 维护状态，人只做关键确认
3. 单个 Task 完整流程：意图 → 执行 → 阶段成果 → 人确认 → 进产物区
4. Task 内一块按时间追加的白板，片段可标 Milestone 或 Master Prompt
5. 外部资料：原文进信息区 → AI 做提要 → 人读原文 → 人的理解转成 prompt 回白板
6. Task 状态机取最常见的五种，不够再加

第 6 条展开就是：`Todo / In Progress / Blocked / Done / Cancelled`，加三道闸门——AI 不能单方面置 Done；中间文件不等于交付；白板状态与 Task 状态解耦。

## 五、现状与未定

### 5.1 已确立

- 项目/任务/Raw/Milestone 的记录写法（Schema.md）
- MS-001：认知形成过程必须完整可追溯
- 项目页 → 任务 → 依据 → 原文 的点击链路，实测通过

### 5.2 未定

| 事项 | 状态 |
|---|---|
| 状态由谁保证 | **本次待定**。Markdown 属性拦不住非法状态，也无事件层，提不出 trigger |
| 前端形态 | 未定：Obsidian 插件 / 独立本地应用 / 手机优先轻应用 |
| 关系语义（supports/contradicts/supersedes） | 提案，只有 supports 在实做 |
| 产物版本字段、归档标记、判断替代 | 提案，尚无实例 |
| 引入 LangGraph 与否 | 研究问题，无结论 |
| 哪些认知发布到共享知识库 | 由人指定，未开始 |

### 5.3 一句话的取舍

**Workspace 的价值不在于保存成果，而在于保住"为什么走到这一步"。** 任何让它多填一个字段、多走一道手续的设计，都要先证明它换来的是这个，否则不加。
